# 累積經驗（通則）— 本套件之開發與驗證

> 本檔屬本套件之累積經驗(通則):預設席位與供應商 id、prompt 長度與批量、測試之根目錄、摘要與分類法重標、檢定標準之判準、評分(bench)、介面與審計所得之教訓。節號與規則 ID 沿用最初編號(故節號不連號),缺號者見索引〈已移出〉。
> 路徑一律為套件內相對路徑;抓取套件 `w-knowledge-capture` 之件寫為「抓取套件之 …」。盤點指令自套件根執行(`git grep`,只搜追蹤檔)。現況以 `sgud/state/state.md` 與 README 為準。

## 1. 預設席位與供應商 id 之漂移（原題:AI 供應商目錄）

- 本套件 `ai` 段不收供應商池(給 `providerPick` 即拋;池屬 `cfg.aiOptions`,為使用端資產),摘要恆以席位(`use`／`fallback`)呼叫 AI;席位於建構期驗可解析,id 打錯啟動即拋(`src/createKnowledgeSummarize.mjs` 檔頭〔啟動期檢核〕)。預設席位 `SUMMARIZE_DEFAULT.ai`(`src/core/summarizeSettings.mjs`)全為 opencode 免費模型。
- **漂移是會反覆發生的形狀**:上游把條目下架或改名,而設定還留著舊 id(使用端曾於數週內遇五次;有條目加入不到一日即移除者)。後果是啟動即拋或整輪不執行,或席位遞補鏈無聲變短。套件預設只能用調度層內建目錄之 id——零設定安裝沒有 `extraProviders`,寫目錄外 id 即啟動拋錯。
- **預設席位 id 變動時要對齊的站點**(盤點:`git grep -nE "mimo-v2|big-pickle" -- src test README.md`;換 id 時以新舊 id 之關鍵字重搜):①`src/core/summarizeSettings.mjs` 預設席位 ②README 之預設席位說明與範例 ③`test/unit-settings.test.mjs` 之預設席位斷言 ④`src/bench/summarizeBench.mjs` 之 JSDoc 範例 ⑤測試中引用目錄 id 之夾具,尤其 opencode 額度日誌夾具之 `modelID`(`test/unit-summarize-assembly.test.mjs`、`test/unit-summarize-log-contract.test.mjs`):日誌之 modelID 對不到目錄條目即不發「供應商額度」字樣,單檔測試看不出,跑全套才紅。
- **限時免費條目視同易失物**:採用前先想好下架時由誰承接、遞補鏈夠不夠長,並預期它隨時消失;免費目錄隨供應方變動(README 已載),實際可用以 `opencode models` 輸出為準。
- **條目仍在目錄,但上游改政策使它 100% 失敗**:解析正常、啟動無警告、與目錄比對也看不出,只能從執行日誌／健康表看失敗累積。本套件預設 `ai.healthStreak: 3`(連續失敗之條目移到鏈尾)只減損耗,不取代檢視。
- **同一故障域不要占太多席**:一家倒下空幾席、遞補後是否仍滿足判定小組「兩票之實際成交供應者須不同」,與分數同樣要看(同家且無不同家第三席者,啟動期警告)。


## 2. prompt 長度上限:安靜失敗、0ms、不計入逾時

- 以命令列傳 prompt 之供應者有字數上限,超過即**未執行就回失敗**(耗時接近 0ms),不像逾時顯眼:健康表上只是多一筆失敗,實際效果是「那個席位從來沒真的工作過」。本套件建構調度層時開 `capability`(`AI_ADAPTER_OPT`,`src/createKnowledgeSummarize.mjs`),呼叫前依條目固有上限剔除放不下者、直接改派遞補,不產生失敗紀錄;注入 `cfg.aiAdapter` 者此預篩屬注入方。
- **prompt 長度＝固定段＋各篇字數總和**:摘要每批字數上限＝`summarize.docsPerCall`×`summarize.charsPerDoc`(預設 3×6,000＝18,000);預篩每篇只給開頭 `summarize.triage.charsPerDoc`(預設 400)字,20 篇約 9k 字、40 篇約 16k 字(`src/core/summarizeSettings.mjs` 預設註解)。改批量、每篇字數、席位數、候選數後都要回頭重量。
- **一律實測,不憑註解或印象估**(註解裡的估計字數與實測可差數倍):`planSummarizeBench(角色)`(`src/bench/summarizeBench.mjs`;不呼叫 AI)回各頁提示詞與指紋,可量實際長度。
- **凡「一次送審／送判」之量也要設上限並分頁**:配額設大即成單一超長 prompt(超過席位上限整輪失敗);中止時已判之頁照樣處置(逐批即存)。


## 7. 批量與輸出截斷

- `summarize.docsPerCall` 預設 3:品質標注擴充後每篇輸出變長,曾見失敗主因為**輸出截斷**;縮批量以控輸出長度,配合「部分接受」(陣列輸出之呼叫逐次給 `acceptTruncated:true`,輸出截斷時收前段完整項目,未涵蓋者記 tries 留佇列)把截斷損失降到最低。物件輸出之呼叫(修補、忠實性覆核)不給——截斷之物件救不回(`src/stages/noteStage.mjs` 檔頭)。
- **輸入與輸出是兩個獨立的上限**:輸入長度受命令列／端點限制(§2),輸出長度受模型回應上限限制。批量同時放大兩者,調批量前要分清楚是哪一邊爆掉。


## 16. 測試之 cwd 與「匯入即執行」

- **套件測試一律自套件根執行**(`npm test`),掃描或逐檔 `import()` 之根一律取自測試檔位置(`path.resolve(path.dirname(fileURLToPath(import.meta.url)), '..')`),不取 cwd(GEN-09)。盤點:`git grep -nE "process\.cwd\(\)|resolve\('\.'\)" -- src test` 應為空。
- **為何**:測試若以 cwd 為掃描根,自別處(如使用端專案根)執行時會走訪並 `import()` 到根外之入口腳本;被 import 者若有頂層副作用(頂層 `await` 跑流程),「import 它」就等於「執行它」——曾因此在使用端專案根啟動了一輪正式流程(寫庫、呼叫 AI)。
- **入口腳本之頂層副作用要擋**:命令列檔以 `isDirectRun(import.meta.url)`(取抓取套件之件)判斷,被 import 時只轉出、不執行(`src/bench/cli.mjs`);`test/unit-summarize-entry.test.mjs` 會 import `src/` 下全部 `.mjs`,依賴此守住。


## 17. 摘要:素材回報、長文與分類法重標

- **樣式判準要拿真實資料校準,不憑想像寫**:「理由直指素材壞了」之樣式(`MATERIAL_PROBLEM_PATTERNS_DEFAULT`、排除樣式 `MATERIAL_EXCLUDE_PATTERNS_DEFAULT`,`src/stores/materialPolicy.mjs`)初版只按自己想到的寫法列,拿真實 skip 理由逐輪比對(命中、僅新／僅舊、含易混字而未命中者、一般反例樣本)後才看到:「頁面載入失敗」「原文被截斷」「語句中斷」「只抓到導覽列」等真素材問題漏網;裸「未載入」會收到「模型未載入預訓練權重」這類題材判斷;「付費牆阻擋…無實質內文」換抓法也救不回(故設排除樣式)。**每次改樣式都重跑同一量測看「僅新／僅舊」兩欄**,並把真實理由原句當單元測試之正反例、合成例另標(`test/unit-summarize-stores.test.mjs` 之 `problemOf` 案)。
- **改名不是新增**:分類法差異若只比「已套用清單 vs 現行清單」,改名之目標會同時被當成新增類別;新增類別之重判範圍是落點類別(通常是最大的「其他」),一次改名即白白觸發大量 AI。差異計算時改名目標(舊名在已套用清單者)須排除於新增(`diffTaxonomy`,`src/stores/taxonomy.mjs`)。**同一事件被兩條規則各自命中時,先問它是哪一種事,再讓一條規則認領。**
- **連續改名以對照鏈宣告**:A→B 之後 B→C,若要求每個新名都在現行清單,安裝方只能把舊宣告改寫成 A→C(歷史就斷了)。故允許鏈(終點須在清單、不得成環),處理時循鏈前進並防環(詞彙檔頭 `src/core/vocab/summarizeVocab.mjs`;`resolveJob`、`taxonomyFixOf`;測試:`test/unit-summarize-stores.test.mjs` 之 `taxonomyFixOf` 案含成環)。
- **裁決之細節要回頭逐條比對後再落地**:退回素材時,實作順手把 `fetchTries` 歸零(理由聽起來合理,與復活對稱),但裁決是「`fetchTries` 不動」(以一次為限控制浪費)。落地前把裁決之「欄位清單」逐欄對過程式,不在實作中途自行加碼(守門:`test/unit-summarize-stores.test.mjs`、`test/unit-summarize-material.test.mjs` 之「fetchTries 與正文不動」)。
- **通用套件之領域字樣檢查連註解也算**:套件原始碼不得含特定產業領域之字樣,註解裡寫一個領域詞也會被擋,常是全套跑才被擋(`test/unit-summarize-domain.test.mjs` ⑦、`test/unit-summarize-package.test.mjs` ③ 掃含註解與日誌字樣;詞表取抓取套件之 `test/tools/domainTerms.mjs`)。**寫套件註解一律用中立詞**(技術文章、方法論內容、「他種要件」「預設之詞」)。盤點:以詞表(`domainTerms`)為準,見 GEN-02。
- **長文做法先選零新 prompt 之路**:map-reduce 要新 prompt＋評比＋額度;「依字數打包、長文獨佔一批」(`packDocsByChars`,`src/stores/packByChars.mjs`)只改批次組成與逐篇預算,字數 ≤ `summarize.charsPerDoc`(預設 6,000)之批,提示詞與未給 budgets 者逐字相同(評分指紋不變),`docsPerCall`×`charsPerDoc`(預設 18,000)字以內之長文即全文進 AI。逾上限者照截但明示(記錄 `sourceChars`／`processedChars`、md 來源章處理範圍、報告計 `truncated`),以 `truncated` 計數決定是否值得做 map-reduce。


## 19. 檢定標準:判準要能在真實資料上逐條核對（含題組、替身與驗收之教訓）

### 判準與掃描

- **比率判準會把違規藏起來**:SS3 正體原以「簡體比例 ≥2%」判,量到的篇數遠少於改以「簡體專用字＋同形字誤用之處數＝0」判者(多數篇只有 1～3 字違規)。**「有問題」以數量定義,不以比例**(不用機率過濾或篩選)。
- **字表／樣式推導須拿真實語料驗,看前 N 名命中之上下文,不是看單元案例過了就算**:字表由 opencc 推導時,標準表會把臺灣通行異體(如「群、峰、床、秘」)判成簡體而大量誤判;opencc 片語表之目標是標準正體,不能當「誤用詞」表(大量臺灣合法用法會被判誤用),偵測改明列表＋跨詞邊界排除,opencc 只用於修正。字表本體與其理由已載於抓取套件之 `textForms` 檔頭,本套件經 SS3 消費。
- **數字紮根(SS4)之誤判幾乎都在「識別碼與格式」,不在數學**:符合度掃描抽核依序找出:理由內以雜湊稱呼他篇(slug 之 8 碼雜湊尾碼)、呼叫端之候選編號(`stripPatterns`)、全形逗號經 NFKC 變千分位、字母後上標(R²)黏後數、年份簡寫(2008-09)、南亞計數(lakh／crore)、12 小時制(3 PM)、爬回之數字黏連、小數點開頭(.041)。**每修一類就重跑掃描再抽核,直到剩下的全是真違規**(模型自補年份、轉述他篇未引之數字、自行推算之數、常識常數);每類寫成迴歸案例。實作與判準見 `src/core/standards/numbers.mjs` 檔頭。
- **抽核要看實例上下文,不看計數**:一批初跑命中數百條,抽十條即見八條是雜湊;若直接把計數當違規數交處置,會撤掉大量合格者。**不合格須無誤判,邊界含糊者列「未能判定」**:嚴式命中才判不合格,只命中寬式列未能判定(`src/core/standards/evidenceRules.mjs` 檔頭〔嚴式不得誤判、寬式寧寬〕)。
- **削弱已審定之標準前先量**:曾以「觸發該路徑之批次『常』是某種情形」為由,把一類排除出覆核;該句沒有任何計數,事後掃庫實際套用 0 筆,依據不存在而還原。「常是／多半」須附數量;放寬標準(少檢一類)比加嚴更需要證據——放寬之錯誤是靜默放進有問題的內容。
- **清單外值不得靜默落後備**:把清單外之值一律改成後備值,看起來只是小偏差,實為把上游壞掉(如某供應者字元層錯亂而產出亂字型別)照收。清單外值只走**明文對映表**(改名表),否則不納入並計數;落後備者須保留原值並可計數,才看得到「被救回／被拒」各幾次、知道供應者壞了。本套件:類別清單外 → 後備類別、原值存 `categoryRaw`(`taxonomyFixOf`,`src/stores/taxonomy.mjs`)。
- **無聲截斷看「上限處的突起」找得到**:任何 `slice(0, N)` 之欄位,先數「恰等於 N」與「N−1」之篇數(自然分布不會在上限處突起);突起即被截,抽樣常見斷在數字中(「…2026-08-」)。修法:於上限內最後句讀處截並記錄,無句讀則全文保留(抓取套件之 `cutAtBoundary`;本套件 `NOTE_FIELD_LIMITS`＋`CLAUSE_END_RE`,截了即記入修正說明;清單欄位逾上限取前 N 項亦記錄;`src/standards/noteNormalize.mjs`)。
- **符合度掃描每輪跑之成本**:掃描(`auditSummarizeStandards`,`src/standards/audit.mjs`;每輪執行由 `summarize.standards.scanEachRun` 開,預設關)之成本隨資料量與實作／範圍改變;「庫再大一倍時重量」若只看資料量,會漏掉「掃描之實作或範圍改變」。新增或改寫掃描之標準後,改後即以代表性資料量跑一次全量並記耗時(掃描剖析曾見單一 slug 正則於長串中文近平方、約占全量 1/10,已等價改寫為 `stripSlugs`,`src/core/standards/numbers.mjs`)。
- **字形修正會連帶改鄰字**:SS3 修正含簡體之片段時,緊鄰違規字之「台」會一併轉「臺」,而不鄰違規字之「台灣」保留——合法而非必要之改字;不改共用件(影響判定),判讀存量處置 diff 時知悉即可。

### 閘、替身與提示詞

- **閘門上線,測試替身要先補成真實形狀;夾具也要過核心規則**:納入閘上線後十餘案失敗,全是替身之理由寫 `'r'`、`'x'`(去標點後 <10 字)——不是功能壞,是替身不合標準;夾具若不滿足被測操作在核心規則之必要條件(例:必填之出處不得為空)亦會第一步即被拒。順序:先寫閘之單元案例(各標準正反兩側),再全套跑,逐一把替身改成合標準之內容;**不可為了讓舊案過而放寬閘**;寫夾具前先查該操作之必要條件(`test/tools/summarizeTestKit.mjs`、`test/tools/noteKit.mjs`)。
- **改組提示詞之程式碼(抽函數、共用區塊)後,驗提示詞逐字不變**(SUM-07):比肉眼比對可靠者——`node test/tools/genPromptGolden.mjs`(只比對標準檔 `test/golden/prompts-default.json`,離開碼 0＝全同)與 `planSummarizeBench(角色).promptFp`(評分題組之提示詞指紋)。指紋一變,既有評比結果即全數失效。
- **AI 之「宣告」不算處置,AI 自報或改寫之輸出一律以產物複驗**:處置若以 AI 起草時之自報為準(例:自報「已處理」「已立爭議」),模型只要寫上就過關;宣告只用於分流,不用於放行。同理「已涵蓋」「已修正」一律複驗:修補後之內容再過同一閘(`src/stages/noteStage.mjs` 檔頭〔欄位定向修補呼叫〕),改寫之理由亦然。**席位聽話不代表輸出合格**(曾有改寫自生無據之數字,被數字紮根閘擋下)。
- **判定小組之替身須讓各席之「實際供應者」不同,票須皆為物件**:小組成立要求兩票之實際成交供應者不同(`decidePanel`,`src/core/standards/panel.mjs`;票之 `provider` 由 `runPanelPage` 之 `call` 回傳的 `providerId` 而來);共用替身若以角色名當供應者,兩個覆核席會被判同一供應者 → 永遠未成立。測試替身以席位條目(`use`)為供應者(`scriptedAi`,`test/tools/summarizeTestKit.mjs`);比較兩票一致時須兩票皆為物件(`sameFaith`,`src/standards/faithCheck.mjs`),否則 `'unsure'` 這類字串被歸入同一類而誤判一致。
- **提示詞範例會被照抄**:範例 `"kinds":[null,"rule"]` 只是示意某方不另立主張,模型卻在兩方皆須給值時照填 null。範例要對應最常見之真實形狀,特殊值(null、空陣列)用文字規則說明而不放進範例;程式端對照抄之值要明文擋下,不靠後備值。
- **判準文字自相矛盾時,模型會在兩邊之間擺盪**:兩句規則對同一案都套得上,同一案時判對時判錯。擺盪(兩次不一致)時先找提示詞內互相衝突之句子,而不是加更多例子。
- **判準本身含糊時,調措辭不會收斂**:措辭三輪此消彼長。換路:①把可判定之部分收斂成封閉清單 ②判斷改為步驟式 ③模型仍偶發越界 → 程式強制(本套件重標:新增類別之工作,非落點之筆記平移至另一既有類別者維持原類別,`retagTargetOf`,`src/stores/taxonomy.mjs`;提示詞亦寫明但不依賴之)。**模型自由度與標準不一致時,用程式收斂,不靠再補一句提示詞。**
- **程式消費 AI 欄位前,先確認提示詞定義了它的語意;補定義也會改變裁決邊界**:程式把某票之 `reason`「用作另一種東西」(例:keep 票之 reason 當新理由改寫)時,若提示詞只對 change 定義 reason,模型常寫「現行理由已點出…」這類評語,過得了形式閘卻不是理由。補定義(「keep 之 reason 亦須…」)會把 keep 與 change 之分界抹平,題組重跑即見。要模型做不同之事時,**改指示之對象(那一項),不改全體共用之定義**,並以題組重跑驗證。

### 題組與真實驗收

- **題組要用安裝方之詞彙,不是套件預設**:題組案之現行型別寫成套件預設之詞,而受測詞彙表是自訂詞彙 → 模型正確指出「不在清單內」,卻被當成模型錯。題組執行器在呼叫 AI 前先驗每案自帶詞彙合受測詞彙表之規格,免得出題錯也燒額度(本套件之評分以抓取套件之 `inputVocabProblemsOf` 搭配 `resolveSummarizeVocab` 驗,`src/bench/summarizeBench.mjs`)。
- **題組全過不等於端對端對**:題組只驗出過題的形狀;新標準上線前必以真實資料在複本跑一批端對端,逐筆看去向(例:重標題組兩次全過,端對端第一批即見「非落點筆記在兩個既有類別間被平移」——題組從沒出過這種形狀),看到新形狀再回補題組(一般案＋未見過之保留題)。
- **題組失敗／不穩先複核出題,不是改提示詞**:①被用來判斷調整方向之保留題一律轉為一般案,另補未見過之保留題;②同一案兩次各判一邊＝案本身判不清(兩邊理由都成立),改列 excluded 附理由、以同形狀而無爭議之新案取代,提示詞不動;一邊明顯錯才是提示詞或模型之問題;偶發不穩如實記錄重跑次數。
- **識別碼不從截斷的輸出補寫**:題組／夾具中的網址、id、檔名一律由程式自來源取值或逐字比對驗過,不靠目視從截斷之列印補完(補完者逐字比對全錯)。
- **品質測試之素材要讓每條標準都走得到**:每條放行判準都要問「這份素材會不會讓它恆真?」(例:素材中恰無任何會觸發某標準之案,該標準在真實 AI 下完全沒被驗);素材改為刻意涵蓋並凍結成固定題組。
- **品質測試要走生產之分批,不只用同一個提示詞函數**:「正式提示詞」包含組裝它的所有參數(預算、分批、材料截斷),不只模板;摘要的批次組成由 `packDocsByChars` 決定,生產、評分(`src/bench/summarizeBench.mjs`)與測試共用同一純函數,否則長文樣本在生產讀到的字數與測試讀到的不同,測的不是正式路徑。評比工具可刻意凍結(指紋),驗收測試不行。
- **真實驗收要隔離單一路徑時,先唯讀試算選題,並用掛鉤隔離,不調門檻**:為只跑一個專步而拉高選題門檻,漏了另一條入選條件(既有待處理量 ≥ 每批篇數即入選),一開跑就是整批真實呼叫。改設定隔離前,先以同一組設定唯讀呼叫選題函式試算「會選到幾個」,為 0 才開跑;或以動作鏈掛鉤(本套件 `cfg.stageOpts` 各子階段含 `tap`)只放行要驗之路徑,不依賴對選題規則之完整記憶(代價:被擋之一般批計入「失敗」,判讀時扣除)。

### 資料處理與存量

- **加欄位前先 grep 該紀錄之全部寫入點**:紀錄若在多處被整筆重寫(首見、換版、重設基準、落帳),新欄位掛上去即被沖掉,要守住得每處各補一行(同一規則手寫多處＝補丁);改為獨立欄位並另列不變式。
- **驗收判準之「新增者」以差集取時,基準不存在＝全部皆新**:check 以 `was && addedIn > was.version` 取新項,新建對象 `was` 為空時全部漏檢,報告卻是「違反 0」。任何前後比對之判準,先問「沒有前值時這條式子回什麼」;漏檢與合格長得一樣。
- **待判要有「條件成立自動結案」之出口**:凡登錄待判(owner 為使用者),要寫明哪個可觀察條件成立時由管線自己結案,並有單元案例;否則使用者照建議做完之後待判仍永掛逾期,題組全過、單元全綠都看不出(交付前把「使用者照建議做完之後下一輪會怎樣」走一遍才發現)。本套件例:文件轉離 raw → 未結之閘門待判結案(`src/stages/noteStage.mjs` 檔頭〔待判〕)。
- **全量預演本身就是測試**:改資料之工具(存量處置),單元案例全綠,對真實規模資料全量預演才看到「擠標籤＋計數尾碼並存」之標籤被修成亂鍵、使該篇失去原分群。先對真實全量預演(`planNoteStockFix`,`src/standards/stockFix.mjs`)看「改了什麼」之分布與異常(如分群只失不得),再談套用;新進同一實作(共用之 `normConcepts`,`src/standards/noteNormalize.mjs`)也有同一洞。
- **修正函數要以「修完再驗一次」測,不只測輸入→輸出一對**:單元案例都是「已知輸入 → 期望輸出」且全過,存量套用後重掃才見殘留——修正某類造出另一類不合格(改單字造出誤用詞,而該類已跑過)。性質測試應是「任一不合格輸入 → 修正後檢查為合格」,樣本須含「修正此類會造出彼類」之字;同一洞也讓新進筆記被正規化後仍判不合格、退回重試。
- **測試注入之日誌字樣須與程式現行輸出逐字相同**:改 WARN 字樣後,字樣表與測試注入若仍是舊字樣,測試仍綠(驗的是舊字樣不被報)而實際 WARN 會被當未知警告。改字樣時 grep 舊字樣於 `src`／`test` 全範圍(`SUMMARIZE_LOG_KNOWN`／`SUMMARIZE_LOG_MUST_SEE`,`src/logContract.mjs`;`test/unit-summarize-log-contract.test.mjs`),測試字樣最好與產生端之單元測試斷言同一字串。

### 驗收與收尾

- **審查報告逐項回到改動處讀碼再接受**:報告寫得完整、測試全綠,但只有讀到分支程式與提示詞對照,才看出契約缺口;審計／複審報告讀的是舊版時,逐條對現碼核——已在實作中處理者不重做,真正新增之缺陷才是工作。接受前至少核:①刪除／撤出類之新行為 ②跨入口共用之雜湊或鍵(不同入口須取同一版本鍵,否則使用者裁示之紀錄被當過時而重核成迴圈) ③提示詞與程式對欄位之約定。
- **每項標準落地即跑全套,不只跑該模組之測試**:只跑相關測試即往下做,直到收尾跑全套才發現前一項留下多個失敗(入口漏掛、案釘住舊形狀);全套(`npm test`,自套件根)比事後回頭判讀便宜。
- **收尾以項目編號機械比對「待辦表 × 進度表」**:宣稱一批做完前,對待辦表每個編號在進度與程式中各找一個落點(grep 編號＋關鍵行為),找不到即未做;不以「批收回」代替逐項。「標準已建」不等於表上那一格已處置——收尾盤查之「完成」須以逐格核實之表為據(逐格附 file:line),不以規則帳本條目存在推定。


## 24. 評分(bench)與等價驗證所得之教訓（原題:摘要抽提為獨立套件）

- **等價要分層驗,且至少一層用真實規模資料**:提示詞逐字差分(標準檔 `test/golden/prompts-default.json`)、子階段行為差分(同輸入同替身)、設定逐鍵之外,再以真實規模資料跑兩邊之掃描與存量預演、逐件全等。夾具差分證明判定一致,真實規模差分才證明「規模與真實資料形狀下仍一致」。
- **同一規則多處手寫,測試端也會發生**:多份各自手寫之「領域中立詞表」每份單看都對,合起來是會各自漂移之規則。共用之測試工具由誰建要先指定;收尾時對測試碼也掃「同一判準寫在 ≥2 處」。本套件之領域詞表取抓取套件之 `test/tools/domainTerms.mjs`,經 `test/tools/captureForTest.mjs` 取用。
- **評分之逐次呼叫選項須與正式呼叫一致**:正式管線之陣列輸出呼叫(預篩、摘要、重標)逐次給 `acceptTruncated:true`,評分角色原本沒給——量到的是「截斷即失敗」之行為,不是正式行為。評分角色以 `callOpt` 補齊。**凡評分／基準,先列「正式呼叫之全部參數」逐項對照**。盤點:`git grep -nE "callOpt: \{ acceptTruncated: true \}" -- src` 應為 3(預篩、摘要、重標;`src/bench/summarizeBench.mjs`),對照正式呼叫 `src/stages/{triage,note,retag}Stage.mjs`。
- **與依賴套件同名之匯出要改名**:摘要之掃描常數若與抓取套件之同名常數並存於下游,易誤取;故為 `SUMMARIZE_AUDITED_STANDARD_IDS`／`SUMMARIZE_AI_PENDING_STANDARD_IDS`(`src/standards/audit.mjs`)。入口測試另以「入口中與抓取埠同一實體之名只准白名單」(`CAPTURE_NAMES_ALLOWED`,`test/unit-summarize-entry.test.mjs`)守住不轉出抓取之件。
- **寫題組會反向發現標準之缺陷**:撰寫通用題組時發現標準(如數字紮根)的邊界判定問題;是否修依「在合約內、已實測、後果具體」三條件,不在等價抽提中順手改(會破壞等價基線);屬正當進位者列設計事實。
- **評分題組抓出產品缺陷:全員都錯的案先查題目與契約**:修補角色一題,多數模型失分且套用數皆 0——查得修補提示詞寫「概念給字串陣列」,而套用端對「概念之一個(第 N 個)」只收字串或 null,模型照提示詞回陣列即全數不採。**一題所有模型都錯,先懷疑題目或「提示詞說的形狀 vs 程式收的形狀」,不是模型能力**;修正後以「依提示詞所寫之各形狀回覆 → 套用端全數採用」之契約測試釘住(`test/unit-summarize-repair.test.mjs` P7)。
- **單次整頁呼叫失敗會把一個角色之分數打成 0;小探測成功 ≠ 實際題可用**:預篩一頁含全部案,一次呼叫失敗(開工即退出、逾時)即使該角色 0 分,而「合契約率正常、呼叫失敗 1」說明是服務面。報告此類格須並列呼叫失敗數,補跑該格,不據以判能力(判準:逐案每回皆＝應然才通過,合契約率、耗時、呼叫失敗只列資訊,見 `src/bench/summarizeBench.mjs` 檔頭〔判準〕)。同理,REST 條目「HTTP 200 卻缺內容」且「短回應正常、長回應全敗」時先懷疑傳輸(如回應被壓縮卻無壓縮標頭而未解壓),不要先懷疑模型:把原始回應以位元組讀出,印全部標頭與前 16 bytes,再逐一試解壓;沒看原始回應就猜成因(如「推理吃光輸出上限」)正是要擋的錯。
- **背景／排定執行之評分行程於啟動時即載入程式碼**:啟動後才改到其會用之碼(含提示詞)不會生效;改碼後須重排或另排一支,多支排定時狀態檔須依計畫區分。
- **免費池額度**:一次 `--role all` 全量可能撐不到底(限流後,後續角色只剩不同池之模型);全量評分分日或分批,多角色時限流之模型不再於後續角色受測(`runSummarizeBenchCli`)。僅要驗證管線路徑(`--cases`＋`--vocab` 通、提示詞指紋與正式同源)時,可用不同池之條目,不必占免費池或等重置。
- **植入缺陷以驗守門偵測力時,在複本上植入**,不就地改產品碼——並行讀取者會讀到壞碼而報假差異。


## 25. 他套件與使用端取用本套件之介面所得之教訓（原題:切換為取自本套件）

- **跨工作之值給在每輪依賴,不只給預設管線之物件**:重標之「保留給後段之時間」(`reserveMs`)若只在預設管線之 `createSummarizeObject({ retag: { reserveMs } })` 注入,`cfg.stages` 自組或直接用工廠者即歸零。故重標「opt 未給取 `ctx.deps.reserveMs`」,由組裝者在每輪依賴給一次;明給之 opt(含 0)優先(`src/stages/retagStage.mjs`)。盤點:`git grep -nE "reserveMs" -- src`。
- **委派逐列操作給本套件時要守全域順序**:回退須全域逆序;`rollbackNoteStockFix` 於所給列內逆序還原、他模組之列略過(`src/standards/stockFix.mjs`)。使用端之帳混有他模組之列時,若先把全部筆記列整批交來回退,「同一套用內先 SS3 修正、後他模組刪除」之筆記會因記錄不在而失敗、或帶回修正後之 md;須在全域逆序迴圈內逐列交付,並以測試釘住(拿掉修正即紅)。
- **把他套件之報告映射進自己之形狀,逐欄問語意,不比欄名**:`auditSummarizeStandards` 之 AI 列 `open` 對 SS5 是「預篩攔下待第二席確認之 raw 篇數」,對 SS9／SS14 才是待判;照名映射成 `holdsOpen` 會印出「待判未結 N」。只映射來源為待判登錄者(`summarizeScanOf`,`src/standards/audit.mjs`);另「全零列」與使用端「有資料才列」之慣例不一致時,也照使用端之慣例收。
- **「全同」要先確認該情境真的走到目標路徑**:改類別名情境首跑時沒有任何筆記落在被改名之類別 → 重標 0 篇、旗標未設、總覽未重建,新舊「全同」卻是空集。替身改為每批首篇落在第一類後,才真的驗到「機械改名 → ctx 旗標 → 總覽重建」。比對器另列刻意字樣差異表之觸及次數,可反證各情境是否真的走到該路徑。


## 32. 審計所得之教訓（原題:套件審計：跨套件共用件之歸屬與只一份）

- **同名異義改名或分列,不硬收斂**:語意不同者(例:同名之兩個測試小工具,一者專測某一路徑、一者為共用機制)改名或分列,硬套共用件會改變被測之行為。本套件例:還原閘與存量處置之 `contentChanged`(只內容章)與 `titleChanged`(標題)兩旗標分列,由下游判「兩者任一為真即須重設基準」(`src/ops/noteRestoreGate.mjs`、`src/ops/noteStockFix.mjs`);合併成單一旗標只是把同名異義搬家。
- **字面常數化擋不住錯名**:讀 report 的子階段鍵若以 map 常數取,錯名亦只得 `undefined`、該欄靜默維持舊值;真正擋得住的是守門。本套件側:`SUMMARIZE_REPORT_KEYS`(`src/logContract.mjs`)與實際 report 之鍵集雙向比對(`test/unit-summarize-log-contract.test.mjs` ④:實際 report 不得有未列之鍵、列了之鍵亦須出現);讀取端(使用端中讀 report 者)宜自備「所讀之鍵 ∈ 該段報告契約」之守門。
- **守門之加項不放寬既有判準,範圍擴大時先盤點新範圍**:數個套件之舊名／沿革／字樣守門統一為一份判準時,各套件原有較嚴之加項(寬式帳本代號、字面日期)保留;改用共用判準前先查擴大後範圍之命中,命中屬路徑資料者才採共用判準。本套件之守門:`test/unit-summarize-package.test.mjs` ④(判準取抓取套件之 `test/tools/historyMarks`,具名例外只一項且仍有對象)。
- **規則歸屬搬家後,README 要跟著改家**:多工作同讀之規則(還原閘之旗標、存量帳之讀法等)寫成一份後,各 README／JSDoc 仍寫舊家名;以規則帳本之站點全集為軸,逐 README 搜舊家名才補齊。
- **替身改以共用機制組成時,逐欄比對結果形狀與判定**:整條管線替身原帶 `preview: ''`、check 以真值判;改以共用機制組成後無 preview、check 以嚴格 `true` 判(同正式調度層)。先查讀者(如 `r.preview || ''`)與各 check 之回傳型別,再記為刻意變更。本套件:`scriptedAi` 之回覆經呼叫端傳入之 check 驗證(回 `true` 才合格,`test/tools/summarizeTestKit.mjs`)。


## 33. 泛用化與語言設定所得之教訓（原題:四套件界定審計：泛用開源套件之視角）

- **先寫界定再審,審的是「違反哪一條原則」而非「哪裡可以更好」**:每條原則附判準(Grep 樣式或測試名)與現況(符合／刻意／違反),矩陣逐站點判定後才定決定;否則審計會滑成無盡的改善清單。「刻意」與「違反」要分開列——刻意者只進 README 已知限制(GEN-20)。
- **每一步都要「預設行為逐字不變」的證據,不是口頭保證**:標準檔(golden)、契約測試、前後差分三者缺一即無從證明 opt-in 沒改到既有安裝。例:把提示詞的「繁體中文」改成 `${L}` 時,摘要之翻譯句「原文為英文時翻譯成繁體中文」若泛化成「原文為其他語言時…」,標準檔與評分所依之提示詞指紋即變——以預設語言分支逐字保留、其餘語言才用泛化句(`src/domain/noteDomain.mjs`)。
- **加一個回傳欄位會打到許多「鍵集恰為」之斷言**:`locale` 進入 runtime 回傳、每輪依賴、`info()`、domain 成員後,多處 `deepEqual(Object.keys(...))` 同時失敗——這類斷言是刻意的契約守門(漏列即失敗)。改契約前先 Grep `Object\.keys\(` 之期望清單(盤點:`git grep -cE "Object\.keys\(" -- test`),比逐一等失敗省一輪全套。`CFG_KEYS` 與讀取者一致之守門亦同(`test/unit-summarize-assembly.test.mjs`):本套件新讀 `cfg.<鍵>` 須列入 `CFG_KEYS`;把整份 cfg 交下來之使用端組裝層也要補鍵。
- **「字形標準不適用」要列為 NA、不能變 0**:正體標準於非繁體中文時若直接不判,掃描總量歸 0 與「全部合格」在報表上無法區分;逐件列不適用(`na` 計數;`checkNote` 回 `SS3` 之 `na`,字樣取抓取套件之 `SCRIPT_NA_DETAIL`)才看得出是語言設定關掉的(`src/standards/noteStandards.mjs`;測試:`test/unit-summarize-locale.test.mjs`)。
- **語言設定要在最底層解析一次、以物件傳遞,不在各處重解析字串**:`resolveLocale`(抓取套件)回凍結物件 `{ code, label, han, script, slug }`,runtime 解析後放入每輪依賴 `deps.locale`,純函數經 `scriptOf(opt.locale)` 取字形政策(未給即預設正體)——既避免各呼叫點各自判語言,也讓測試能以字形政策物件直接注入。`Intl.getCanonicalLocales` 驗代碼、`Intl.DisplayNames` 取表外語言之稱呼,不手列全部語言。
