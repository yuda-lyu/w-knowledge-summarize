### 1.1 第三種形狀:條目還在,但上游改政策使它 100% 失敗

2026-09-18 04:00 起,**opencode 自家免費層**對外斷供:CLI 回 exit 1、REST 回 HTTP 403,訊息一致——

> `Error from provider (Console): OpenCode's free tier can only be used from within OpenCode`

**斷供範圍的分界線是「金鑰屬於誰」,不是「走不走 opencode CLI」**——這點一開始我判斷錯,經使用者質疑後實測釐清.條目 id 的第二段即供應商:

| 實測(`node tmp/probe-union-alpha.mjs <id>`,該腳本吃任意 id 並印 stderr) | 金鑰／供應商 | 結果 |
|---|---|---|
| `oc:opencode/muse-spark-1.3-contributor-free`(CLI) | `OPENCODE_KEYS`／`opencode` | ✗ 11s exit 1 |
| `zen:muse-spark-1.3-contributor-free`(REST) | `OPENCODE_KEYS` | ✗ 1s HTTP 403 `FreeTierError` |
| `zen:mimo-v2.5-free`(REST) | `OPENCODE_KEYS` | ✗ 403 同訊息 |
| `oc:opencode/deepseek-v4-flash-free`(ds4f) | `OPENCODE_KEYS`／`opencode` | ✗ 5s exit 1 `UnknownError` |
| **`oc:agnes-ai/agnes-3.0-flash`(CLI)** | `AGNES_KEYS`／`agnes-ai` | **✓ ok 14s** |
| **`oc:poolside/poolside/laguna-s-2.1`(CLI)** | `POOLSIDE_KEYS`／`poolside` | **✓ ok 8s** |

即:**被擋的只有 `provider: 'opencode'`(`OPENCODE_KEYS`)那一族**;用自己的 agnes／poolside 金鑰走 opencode CLI 完全正常——opencode 此時只是傳輸層,請求送到各自家的端點.**沿用本機 `auth.json` 登入亦被拒**(對 opencode 那族而言不是金鑰問題,是政策).

**因此 `oc:agnes-ai/*` 與 `oc:poolside/*` 是同一上游帳號的替代傳輸路徑**:直連 REST 端點劣化時(agnes 有前例)可改走它,但**不增加額度也不增加多樣性**(同一帳號、同一模型),排席位時不可當成另一家.

**當日 14:4x 解除(w-dispatch-ai 1.0.30)**:閘門是以**「呼叫端的 config 裡有沒有 bash 工具」**判定是不是 opencode 本體;套件改為注入 `OPENCODE_CONFIG_CONTENT` 且 `bash: 'ask'`(而非 `'deny'`)即通過.本機實測 `oc:opencode/muse-spark-1.3-contributor-free` **ok 8s**,muse 隨即回任兩席.

但這條路的性質要記清楚:

- **只有 CLI(`oc:`)路徑通,REST(`zen:`)仍 403**——REST 無法偽裝成本體.
- **它依賴上游目前的偵測方式**:上游只要改判定(例如改檢查別的特徵),就會再次斷供.故**不把某一家放到太多席**,且遞補鏈要保留非 opencode 家(目前審計席 luna 即為此).
- `oc:opencode/deepseek-v4-flash-free`(ds4f)**不在此列**:它回的是 `UnknownError` 伺服器錯誤,與閘門無關,閘門解除後仍不可用.

**這種形狀比「條目被移除」更難察覺**:`providerPick` 解析正常、啟動期無警告、`verify-pkg-upgrade.mjs` 也不會報——只有**健康表**看得出來(`ok=0` 而 `fail` 累積).當時 muse 身兼**三個席位**(起草3、audit、revise),每輪白繳 18 次失敗再全數遞補到 sonnet(有 5 小時 session 上限的那家),連續 10 輪無人發現.

**巡檢為何沒告警——兩種都會漏的判準(已修,`srcPack/ops/patrol.mjs` ⑬;現位於套件 `w-knowledge-extract/src/ops/patrol.mjs`)**:

| 錯誤判準 | 為什麼漏 |
|---|---|
| 靠「連續失敗被降序」(`cooled > 0`) | 冷卻只由 429／逾時觸發,**`exec`／`http` 型失敗 `cooled` 恆 0**.同日 union-alpha 有被降序所以報得出來,muse 沒有,所以整天靜默 |
| 靠「整日聚合 `ok === 0`」 | 會被「早上正常、下午全敗」抹平.muse 當日聚合 **ok 36／fail 162**,`ok > 0` 直接濾掉——我第一版就是這樣寫的,在真實資料上驗證時才發現只抓到 union-alpha |

正確判準是**末端連續輪數**:逐輪掃健康表,同一 id 連續 ≥2 輪 `ok=0` 且該段失敗 ≥6 次即告警(門檻 `deadProviderFailMin`／`deadProviderStreakMin`).以此對真實日誌重跑,即報出「muse 連 9 輪、敗 162」.

**教訓**:①**健康表是唯一能看出這種形狀的地方**,巡檢必須逐供應商看、且要看趨勢不只看聚合;②新寫的告警一定要**拿真實日誌重跑驗證**,不能只靠自己編的單元測試資料——我的第一版通過了自己寫的測試卻抓不到真的那一家.

**教訓與作法**:

1. **每次套件升版後跑 `node tmp/verify-pkg-upgrade.mjs`**,它會逐一比對 `providerPick` 與內建目錄並列出差異.不要只看 `npm i` 成功.**但它只抓「條目被移除」,抓不到 §1.1 那種政策變動**.
2. **升版與排程輪次會搶時間**:升版後到下一個整點之間若沒驗,壞的就是整輪.時間允許時,升版後立刻驗.
3. **限時免費條目視同易失物**:採用前先想好下架時的退路(誰承接、遞補鏈夠不夠長),並預期它隨時消失.壽命可以短到一天.2026-09-22 之後**現役七家**:agnes／poolside(自有帳號、免費、REST 直連,不受 opencode 政策影響)、agy(CLI,30k 上限)、sonnet／luna(訂閱制 CLI,有 5 小時 session 上限;luna 自 09-23 起為 gpt-6-luna,經 extraProviders 自帶)、muse／mimo-v2.6(opencode CLI,免費,但依賴 §1.1 之閘門繞道;mimo 09-22 評比七席全 ◎ 後入池,坐整合並作各席 sonnet 前之免費遞補——兩者同一故障域,不因此多算一家).**倒掉的是 opencode 自家免費層,不是「免費模型都沒了」**——這句話我第一次寫錯過,更正見 §1.1.
4. **同一家不要同時坐太多席**:muse 一家倒下就空了三席(起草3、audit、revise),全部壓到 sonnet.排席位時看的不只是分數,還有**故障域**——一家死掉會空幾席、遞補後是否仍滿足換家原則.
5. 「不重要」的備查條目(如已知不可用但留著登錄)同樣會拋錯,**留著就要跟著上游變動維護**,否則不如刪掉(09-18 已據此把三條死掉的免費層條目自 `providerPick` 移除,備查資訊留在本檔).
6. `extraProviders`(安裝方自帶條目)與內建目錄**不要同時定義同一個模型**——兩處定義必然漂移.套件收錄之後就移除自帶的那份(`verify-pkg-upgrade` 會提示).
   **2026-09-23 實例**:`codex:gpt-6-luna` 在 codex CLI 可用、但 1.0.35 目錄只收 gpt-6-sol,兩專案皆以 extraProviders 自帶(欄位照抄內建同族條目,`sandbox:'read-only'` 不可省).接自帶條目要**三處都帶到**:本專案 `settings.json`(adapter 經 `ST.ai` 自動讀);tai-news 的 `settings.json` **與其 `src/ai.mjs` 之 `createAiCaller` 參數**(原本沒傳,不補則條目不生效);本專案 `smoke-tai-news.mjs`(它照 tai-news 另建一份 caller,漏帶會誤報 missing).**套件預設 `settingsDefault.AI_DEFAULT` 只能用內建目錄之 id**——零設定安裝沒有 extraProviders,寫進去就是啟動即拋.
   另:codex 為訂閱帳號、**與使用者本人共用額度**(09-23 18:2x 實打時已用盡,「try again at 6:34 PM」),不要在額度緊時跑它的評比.
7. **小探測成功 ≠ 實際題可用;REST 條目「HTTP 200 卻 missing content」先懷疑傳輸,不要先懷疑模型**(2026-09-24 `zen:space-bunny-free`):開工前探測(小 JSON)2.1s 正確,正式評比 14 題卻全敗.直打重現:HTTP 200、本體是 brotli 壓縮位元組、回應**沒有 `Content-Encoding` 標頭**(Node fetch 看到 0 個標頭)——fetch 不解壓 → 轉接器 JSON 解析失敗 → `INVALID_RESPONSE: missing choices[0].message.content`;以 brotli 手解即為完整正確之答案(finish_reason=stop),改帶 `Accept-Encoding: identity` 則直接回原文 JSON.小回應未被壓縮,所以探測過得了.**診斷法**:把原始回應以位元組讀出,印全部標頭與前 16 bytes hex,逐一試 gunzip／inflate／brotli／zstd(當時腳本即此法).我先猜「推理 token 吃光 max_tokens」,是錯的——沒看原始回應就猜成因,正是這條要擋的.
   **同形第二例是生產故障**:agnes 自 09-23 19:00 起長回應被 gzip 壓縮而無標頭(前 bytes `1f8b`),本專案提煉段零成交近 20 小時,tai-news 短摘要不受影響.w-dispatch-ai 1.0.37 起 REST 轉接器預設帶 `Accept-Encoding: identity` 已根治(`模型使用與評比.md` §5.20).**同一條目「短回應正常、長回應全敗」即此症之指紋**.
9. **巡檢告警只寫進紀錄檔,本專案沒有推送(`.env` 無 `TELEGRAM_*`)**(2026-09-24 起:最新一則在 `最新監控運維紀錄.md`,歷次在本檔【監控】部末;下文「該檔最後 3 筆」即指【監控】部末 3 則)——agnes 零成功自 09-23 20:47 起每次巡檢都列、到 09-24 08:39 已「連 9 輪」,同期 mimo／muse 也連 8 輪零成功,全都沒人處理,直到 09-24 14:2x 因別的任務查日誌才發現.**接任何任務(尤其升版、評比、改席位)先讀該檔最後 3 筆**,有「零成功」「降序」「未列入已知常態」就先查再動手.
8. **讀遞補結果之錯誤訊息要看「最後一筆」是哪一把金鑰的**:同一條目有多把金鑰時,`INVALID_RESPONSE`／HTTP 錯誤會換下一把、以**剩餘預算**重打(`TIMEOUT`／驗證失敗才整組跳過,`dispatchAiFallback.mjs` 檔頭分流規則).故評比格記「TIMEOUT after 66.9s」而該格實耗 360s,表示第一把先以別的錯誤失敗、第二把用剩下的 67s 逾時——第一次就逾時的會是「after 360s」.只看最後一筆會把傳輸缺陷誤讀成「模型太慢」.


## 2. prompt 長度上限:安靜失敗、0ms、不計入逾時

`agy:`(antigravity CLI)**以命令列傳 prompt**,`dispatchAntigravity.mjs` 設 `MAX_PROMPT_LENGTH = 30000`(Windows 命令列 32,767 上限扣掉 exe 路徑與旗標之保守值).超過就**未執行即回失敗**(errorType `params`),耗時接近 0ms——不像逾時那樣顯眼,健康表上只是多一筆失敗,實際效果是「那個席位從來沒真的工作過」.

**踩過三次,都是同一個原因、不同席位**:

| 席位 | 實測 prompt 長度 | 結果 |
|---|---|---|
| 關聯(6 篇 × 25 候選) | **40,191～43,814 字元** | 每輪 9 次呼叫全數 params,全由 sonnet 承接.候選數改 15 後為 25,017～27,732,主力可用 |
| 提煉起草 | basePrompt 17k＋ | 固定超限,2026-09-12 改派 |
| 提煉整合(任務＋四份候選) | 17,052／21,423(2026-09-18 實測兩樣本) | 曾「每輪固定超限」,遂於 09-12 改 sonnet |

**量測到的真值(2026-09-18)**:整合 prompt 長度 ＝ **各候選字元總和 ＋ 511**(兩樣本皆精確吻合);單份候選 3,680～6,413 字元.故**起草席位數直接決定整合輸入長度**——四席約 17～21k,三席約 13～16k.

**兩條路徑對超限的處置不同(這點很容易誤判)**:

- `callJson`(萃取／關聯／預篩)→ 經套件 `src/ai/capability.mjs`(原 `srcPack/ai/capability.mjs`)的 `fitChain`,**呼叫前**依實際 prompt 長度把放不下的條目剔除,直接改派遞補,不會產生失敗紀錄.
- `getWkf()`(提煉工作流)→ **不經** `fitChain`,超限時是 agy 回 `params` 後才遞補.成本仍低(未 spawn),但會計入健康表.

**教訓**:註解裡寫的「約 1.5 萬字」實測低估三倍.**prompt 長度一律實測**(`tmp/measure-prompts.mjs` 對真庫量),不要憑印象估;改動候選數、批量、席位數時都要回頭重量.


## 7. 批量與輸出截斷
